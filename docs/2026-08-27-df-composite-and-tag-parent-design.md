# Oracle-divergence fixes — the D/F composite and the tag-parent verdict

**Date:** 2026-08-27 · **Status:** IMPLEMENTED and oracle-verified in `04245f5...HEAD`. Both defects lived inside the unreleased `v2.1.0..HEAD` range, so neither divergence shipped. The design was approved before implementation and mandated harness-first development: the behavioral claims began as analysis-only hypotheses, the differentials ran before the fixes, and the measured outcomes are recorded below. The design conversation was Claude Code session `3b243a1b-9bdf-40a1-b810-208a2c2ce2ef`; this document carries the durable decisions because those transcripts expire. The 2026-08-27 two-reviewer amendment added the fixture-escape constraints on TPC-1/TPC-4, TP-3′'s uniform retain rule, DFC-3's relabeling from measured to hypothesis, and the corrected provenance retained in the decision record.

## The doctrine this doc is written under

Claims labeled as hypotheses record the design-time state before measurement. The repo's standing harness/oracle-first rule determined the implementation: extend the differentials, drive real git side-by-side, and let the observed transcript decide. The fix target remained "match the oracle," never "match the analysis."

## Implementation outcome

- DFC-1 measured the predicted composite in both wire orders: canonical git and pggit accept the fast-forward update of `refs/heads/a` and reject the doomed creation of `refs/heads/a/b`.
- DFC-3 measured deepest-wins for the three-name chain in both tested orientations, confirming the single-pass phase-2 rule.
- TPC-1 and TPC-2 measured receive-pack rejecting the tag-parent commit through the client-readable per-ref connectivity channel; pggit returns HTTP 200 rather than crashing.
- TPC-3 exposed a deliberate transcript difference after the shared receive rejection: canonical upload-pack accepts a direct want for the stored malformed commit and then aborts during pack construction without an in-band `ERR`, while pggit validates closure before packing and returns a clean in-band refusal. The contract is refusal without a pggit transport fault, not byte parity on this path.
- The implementation landed in the named DFC/TPC harnesses, the two ordered receive-pack phases, and the classification/retain paths of `fullClosure` and `originClosure`. Follow-up commits tightened role-overlap handling and judged policy by final observable state without changing the approved behavior.

## The two defects, each in one paragraph

**DF — the directory/file composite.** `handleReceivePack` (src/protocol/receive-pack.ts) judges D/F conflicts last, correctly, because deepest-wins is the pipeline's only inter-command rule. But the pre-fix `losesToDeeper` judgment read `eligibleNames`, a set frozen BEFORE the existing-namespace clash check ran — so a deep sibling that was itself doomed against an existing ref still defeated a valid shallow command. Composite: `refs/heads/a` exists; one push carries `update a` (clean fast-forward) + `create a/b`. Pre-fix pggit: both ng (`a/b` for clashing with existing `a`; `a` for losing to the still-"eligible" `a/b`). Oracle result: `a` ok and `a/b` ng in both wire orders. The durable constraint is that a rejected command must not reserve the namespace against a valid sibling.

**TP — the tag-parent verdict.** A pushed commit whose `parent` header names an annotated tag is a malformed graph (parents must be commits), and because the pack ingests before policy, both objects land in storage — the tag WITH its healthy `git_tag` row. The pre-fix walks (src/store/reachability.ts) bucketed the parent oid as commit-expected; step 2's `git_tag` probe covered only the `unknown` bucket, so the exonerating row was never read; step 3's `git_object` probe found type TAG, and `judgeProbedType`'s TAG-with-commit-expectation cell returned `"corruption"` → `throwMissingDerivedRow` → an uncaught crash claiming the chunk-1 invariant was broken. It was not: the row existed; the walk just never consulted it. Blast radius: connectivity 500ed the push, a have-less serve of the stored orphan 500ed, and a GC pass over a reachable instance of the shape crashed (a reachable instance arose only through the direct-API seeding path — the wire never applied a ref over the shape, since connectivity failed first). The same shape at a boundary tip was already handled correctly (`boundarySatisfies` → violation → clean rejection) — the in-walk path and the boundary path disagreed about one policy. Oracle result: receive-pack rejects the push through a client-readable per-ref connectivity result, never a transport fault.

## Decisions

- **DF-1 — Count the concepts: existing-clash is a per-command check; deepest-wins is inter-command.** The fused loop holds two concepts under one judgment and one reason string, and the bug lives at their fused boundary. Split: phase 1 judges `clashesExisting` (depends only on the fixed existing namespace, symrefs included) alongside the other per-command disqualifications; phase 2 judges deepest-wins ONLY over phase-1 survivors. The rejection reason stays `"funny refname (directory/file conflict)"` for both concepts unless the oracle's comparison depth says otherwise (DF-3). The phase-2 survivor predicate carries EVERY per-command verdict — including the fast-forward check, which the pre-fix phase-1 predicate omitted: an FF-failing deeper sibling is unreachable in a D/F composite today (a deeper UPDATE implies the deeper name exists, which dooms the shallower against the existing namespace first), but leaving FF out keeps the same stale-set class open to a future policy change, and including it costs nothing.
- **DF-2 — Single ordered pass; no fixed-point iteration.** The dependency is one-directional and the code comment must carry the argument: `clashesExisting` reads only the fixed existing namespace, so filtering by it first is final; deepest-wins over the fixed survivor set is a sound pairwise judgment even for chains (`a`, `a/b`, `a/b/c` all new: `a` and `a/b` each lose to the deeper survivor `a/b/c`, one pass). Removing a loser can never create a new loss, so no iteration is needed.
- **DF-3 — Report parity is judged at the existing differential's comparison depth.** The policy differential is `src/generative/receive-pack-policy.test.ts` — the code comment names no file; the attribution was verified by reading it during the 2026-08-27 audit (its in-batch D/F case, a two-name pair with the deeper ref sent second, sits at :644) — and this fix adopts its per-ref ok/ng comparison depth. No assertions on git's reason-string PROSE: that wording is upstream text free to drift, so pinning it buys flake, not parity.
- **TP-1 — Corruption verdicts must be proof-backed; the fix is in the walk, not the judge.** In `fullClosure` and `originClosure` step 2, the `git_tag` probe extends to commits-bucket misses (oids commit-expected but without a `git_commit` row) as a CLASSIFICATION probe, reusing `loadTagTargets`. Found ⇒ the edge lied: a typed-edge violation, exactly the vocabulary the walks already carry. Not found ⇒ the oid proceeds to the object probe, where a TAG result now PROVES the derived row absent — `judgeProbedType`'s code is untouched; only its comment updates, because its corruption cell has become true by construction.
- **TP-2 — Reject-mode semantics: the violation takes the existing reject path.** Under `"reject"` (connectivity, and `fullClosure`'s serve semantics where violation ⇒ missing): the oid lands in missing, is never traversed, and the push fails per-ref with the existing "missing necessary objects" channel — the same class of client-readable rejection measured from canonical git.
- **TP-3′ — Retain-mode peels EVERY retained tag violation (AMENDED 2026-08-27; supersedes TP-3).** The original TP-3 traversed only the commit-parent shape and justified it as "mirroring retain's standing stance" — the audit showed that stance does not exist in code: retain's post-violation expansion is trees-only, so a TAG kept under violation is never peeled today, and the sibling shape — a tree entry naming an annotated tag — leaves the tag live while GC can sweep its TARGET from under the surviving `git_tag` row (`git_tag` carries no FK on `target_oid`). The uniform rule replaces both special cases: under `"retain"`, ANY tag-typed object kept as a violation resolves its target through `loadTagTargets` (a row missing at THAT probe is genuine, proof-backed corruption — loud) and the target is traversed with the violator's origin bits; the epoch stays withheld either way. This makes the code's own comment — retain "expands by its ACTUAL type" — true for tags instead of false-for-tags, and closes a pre-existing GC data-loss path. Reject-mode is untouched for both shapes (violation ⇒ missing ⇒ refusal). Provenance: the owner delegated this ruling (with the sequencing and findings-note rulings) on 2026-08-27 to the criterion of highest correctness, idiomaticness, adherence to this repo's engineering principles, and lowest overall system complexity; the uniform rule is what that criterion selects: one rule, no documented gap, and the comment stops lying.
- **TP-4 — The boundary path is untouched.** `boundarySatisfies` already returns violation for a TAG meeting a commit expectation; after TP-1 the in-walk and at-boundary verdicts agree, which closes the inconsistency that was the original smell.
- **TP-5 — Rejected alternative: typing parents at ingest.** Rejecting `parent <tag>` in ingest-validation looks tempting and is wrong twice over: the ingest boundary cannot type a parent (the parent object may be absent — in neither the pack nor the store — which is ordinary, not malformed), and canonical git's DEFAULT receive path does not fsck-type parents either (`receive.fsckObjects` defaults off; connectivity arbitrates). The walk is the correct layer.
- **Anti-decisions, named.** No catch around `throwMissingDerivedRow` anywhere — a catch would launder REAL corruption (a genuinely missing derived row) into a polite client message, and the loud channel's value is that it fires only on true storage breakage (pinned by TPC-5). No "un-reject the shallower command if its deeper sibling was rejected" special case — the reorder IS the root-cause fix; a compensating branch is the symptom patch this repo's bug-fix protocol exists to prevent.

## The mechanism

**DF.** In `handleReceivePack`, the D/F block is split into two ordered loops: first, each command passing the established phase-1 predicate is judged against `existingNames` alone (same prefix test, symrefs included) and disqualified into `nameProblem` on a clash; second, `perCommandSurvivors` is computed from every per-command verdict including the existing clash, and `perCommandSurvivorNames` supplies the deepest-wins judgment. Everything downstream (`evaluated`, the decision union, apply/report) is untouched.

**TP.** In both walks' step 2, the unknown-bucket and commit-expected `git_commit` row misses form `tagProbe`, the batched `loadTagTargets` input. A commit-expected hit is classified, never resolved as an ordinary tag: `fullClosure` adds it to `missing` and does not traverse (its violation-⇒-missing convention); `originClosure` adds it to `violations`, and then per mode — reject: `missing` + mask scrubbed, no traversal; retain: mask kept, target enqueued as unknown with the oid's bits. The loaded tag row is the level's single actual-type verdict for that OID: if the OID also carries unknown or object-bucket roles, those roles fold into the same classification and their origin bits are preserved instead of re-probing the tag through `git_object`. Judged tag hits are excluded from step 3's object probe; tag misses flow to step 3 unchanged, so any TAG reaches `judgeProbedType` only after its `git_tag` row misses. Under retain, step 3's object-only TAG violations (the tree-entry-naming-a-tag shape) get the same treatment one probe later: a batched `loadTagTargets` over the retained tag violations resolves their targets for traversal, and a row missing at that probe is genuine corruption, loud. `ancestry`'s SQL corrupt probe and `peelRef` cannot crash on this shape because both consult `git_tag` directly by oid; `ancestry`'s separate permissiveness on the malformed edge remains the named concern deliberately outside this fix.

## The observable contract (normative — the test spec for the harness-first phase)

Same doctrine as the scheduler docs: observable surfaces only (the git-protocol oracle, Postgres rows, returned results), no internals asserted. Prefixes `DFC-*` / `TPC-*`.

- **DFC-1 — Composite parity.** Repo with existing `refs/heads/a`; one push carrying `update a` (fast-forward) + `create a/b`, in BOTH wire orders: pggit's per-ref report equals canonical git's for the same push. Measured result: `a` ok, `a/b` ng.
- **DFC-2 — A doomed-deeper never reserves the namespace, whatever doomed it.** Variant where the deeper sibling fails a DIFFERENT per-command check (e.g. connectivity): the shallow valid command still applies. This was already true before the fix for every check the phase-1 predicate carried (fast-forward was the one omission — closed by DF-1's widened survivor predicate); pinned so the reshape cannot regress it.
- **DFC-3 — In-batch chains.** All-new `a`, `a/b`, `a/b/c` in one push, BOTH wire orders, fresh oracle repo per order: pggit matches canonical git's measured deepest-wins result.
- **TPC-1 — Push rejection parity.** A push whose pack carries an annotated tag plus a commit naming that tag as `parent`: pggit responds with the same client-readable per-ref connectivity rejection class measured from canonical git, never an HTTP 5xx. Variant: the tag is already in the store from a prior push and only the malformed commit is in the pack; no ref may name the tag because a tag ref tip sits in the connectivity walk's stop set and takes the separate boundary path instead of exercising the in-walk verdict.
- **TPC-2 — Boundary variant unchanged.** A new commit whose parent is an existing ref TIP that is an annotated tag: the already-correct boundary rejection stays byte-identical.
- **TPC-3 — Serve refusal, not a crash.** With the malformed pair stored as denied-push residue, a have-less fetch wanting the malformed commit is refused through the existing want-refusal channel (ERR, HTTP 200), not a 500.
- **TPC-4 — GC survives the shape and withholds the epoch.** Seed the malformed pair REACHABLE (via `insertObjects` + `setRef`, the sanctioned non-wire seeding path — the wire can never create a reachable instance, since connectivity now rejects it), with the ref pointing at the malformed COMMIT only, never at the tag (a tip-tag becomes a walk ORIGIN and dodges the in-walk verdict — the same fixture-escape as TPC-1's variant): `gc()` completes without throwing; the tag object AND its target survive the sweep; the pass's epoch outcome is `cleared`; the drain's next pass is unaffected.
- **TPC-6 — The sibling shape under GC (TP-3′'s second half).** Seed (same non-wire path) a reachable tree one of whose entries names an annotated tag: `gc()` completes; the tag AND ITS TARGET survive the sweep; the epoch outcome is `cleared`. Pre-TP-3′ the target was sweepable under the surviving `git_tag` row — this is the data-loss pin.
- **TPC-5 — Real corruption stays loud.** With a `git_tag` row surgically deleted from under a stored tag object, the walks still crash with the derived-row invariant error. The fix sharpens the trigger; it must not soften the response. Existing coverage already pins the adjacent cases in `src/e2e/typed-graph-policy.test.ts` (:96 and :142 at the 2026-08-27 audit read) — extend THERE first rather than duplicating the concern into a new file; the only genuinely new pin is a deleted row behind the new classification probe.
- **Preservation.** The receive-pack policy differential, the negotiation and served-set differentials, and the full battery remain the regression surface.

## Implementation notes

### Decided — implementation

- `perCommandSurvivors` is computed AFTER existing-clash disqualification, and `perCommandSurvivorNames` is derived from it; the mid-loop mutation of `nameProblem` for in-batch losses may remain as the write mechanism, but no judgment reads a set that a later filter can invalidate.
- Existing-clash stays gated on the same pre-fix phase-1 conditions (name well-formed, connected, valid tip, non-delete), so the reason precedence a doomed command reports is untouched — a command failing connectivity AND clashing an existing ref still reports "missing necessary objects", exactly as today. The composite case is the DF fix's ENTIRE behavioral delta; anything else moving in the per-ref report means the reshape went wrong.
- The TP fix is deliberately ASYMMETRIC: only the tag side gains a classification probe. A commit-expected oid is already `git_commit`-probed in step 1 before it can reach step 3, so a COMMIT type code at the object probe with a commit expectation is already proof-backed corruption — symmetrizing with a redundant commit-side probe adds a read that can never change a verdict. Rejected: "probe both for consistency."
- The TP classification probe reuses `loadTagTargets` verbatim and widens its existing batched input with commit-expected row misses. Healthy graphs have no such misses, so their database query count and input are unchanged; retain-mode traversal reuses the target that probe already returned rather than reading it twice.
- The change is bounded to `fullClosure` and `originClosure`. `frontier` and the want-router are deliberately untouched: the router types wants directly and peels TAG wants through `peelTagChain` (a want that IS the tag is unaffected), and `epochServe` already falls back for non-commit non-tip wants.
- `judgeProbedType`'s code is untouched; its TAG-with-commit-expectation comment is rewritten to state the now-true precondition (only row-less tags reach it with a commit expectation).

### Nuances

- The obvious implementation of the TP probe is the exact wrong turn: a commits-bucket hit in `git_tag` must be CLASSIFIED, never resolved-as-a-tag and traversed. Traversing (under reject/serve semantics) would ACCEPT the malformed graph — connectivity would verify through the tag and the serve would ship it — where canonical git rejects it. Classification and resolution look interchangeable at that call site and are not; only retain-mode traverses, and only because GC must not sweep what an edge (however malformed) still names.
- The DF defect is a STALE-SET bug, not an iteration-order bug. The pre-fix loop mutated `nameProblem[i]` mid-iteration, which read like order-dependence and was not: the survivor-name set and `existingNames` were both precomputed, so no iteration's verdict fed a later one. Diagnosing (or testing) it as order-sensitivity chases a ghost — DFC-1's both-wire-orders clause is parity with git, not a determinism probe.
- `frontier` needs no parallel change: a parent with no `git_commit` row loads as `null`, is marked missing, and acts as a boundary, so a have-ful fetch already refuses cleanly through `routed.missing`. The corrected crash paths were `fullClosure` and `originClosure` (have-less serve, connectivity, GC).
- Retain-mode traversal must inherit the violating oid's origin BITS into the enqueued target, or the epoch masks under-count reach — and the epoch is withheld regardless (violations non-empty), so this matters for the live set, not the bitmaps.
- `fullClosure` has no `violations` set by design; violation-⇒-missing is its standing convention and the TP fix follows it rather than adding one.
- TPC-4's reachable-shape seeding goes through `insertObjects` + `setRef` only; do not "improve" the fixture by weakening wire-path validation to push it.
- DFC-2 remains a preservation pin, not behavior introduced by this fix.

### Traps

- The policy differential's oracle transcripts are order-sensitive: DFC-1 uses an identically seeded fresh oracle repo for each wire order so the second orientation never measures a namespace mutated by the first.
- Biome reformats SQL template literals when a backtick appears inside a SQL comment (the migration-0008 incident); the TP edits sit near `sql` templates — no backticks in SQL comments.
- `git hash-object --literally` stores the malformed oracle objects, and canonical `pack-objects` builds the single pack fed unchanged to both receive implementations.

### Concerns

- The TP walk edit touches both closure functions' hottest loop; the serve differentials and the perf probes are the regression net if the extra set arithmetic shows up at scale (expected: zero-cost on healthy graphs, per the Decided note).
- A thread noticed and deliberately not pulled: `ancestry()`'s recursive CTE steps through `git_tag` targets with no edge-type judgment, so on the malformed graph it traverses THROUGH a tag-parent edge — no crash, but `isAncestor`/`readyToGiveUp` become slightly more permissive than git's parse-failing walk would be. Out of the two fixes' scope; only worth revisiting if an oracle differential ever pins a divergence there.
