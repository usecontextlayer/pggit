## The problem, in one paragraph

pggit stored every git object fully inflated and re-deflated each one on every clone, never emitting deltas — a deliberate original design ("spec §3.4 asymmetric kernel", now retired). On a repository whose history is dominated by an append-only directory (one run-UUID subdir added per commit — the shape of CodeCreators' `komal` workspace repo, pggit's motivating production tenant), tree bytes grow quadratically with history: the same growing tree object is rewritten whole by every commit, and trees are ~20-byte binary SHA-1s that intra-object compression cannot touch (lz4 recovers 3% on them — the original schema bet that lz4-TOAST substitutes for delta compression is empirically false on this workload). Measured consequence: a 2 MB-content repo served as a 53.6 MB pack, ~2.4 s of zlib CPU per clone re-deflating unchanged bytes, and a production cold clone racing a 4,950 ms react-router streamed-loader deadline and intermittently losing (customer-visible render failures).

## What was built (the mechanism)

Git's own architecture has three stages: write objects whole, repack offline into delta-compressed packfiles, serve by copying stored bytes. pggit had stages 1 and 3 and no stage 2 — every downstream cost was a symptom of that missing middle leg. This change builds it, as a **derived tier**:

- **`git_pack_encoding`** (migration `0008_pack_encoding.ts`): at most one row per object — `data` is deflated bytes served verbatim (deflate(raw) when `base_oid IS NULL`, deflate(delta program) otherwise), `data_size` is the inflated length of what `data` holds (pack-header varint semantics — the delta PROGRAM length for a delta row, NOT the object's size; `git_object.size` cannot serve both meanings). Hash-partitioned ×16 like its siblings, `STORAGE EXTERNAL` on `data` (already-compressed bytes get no second compression pass), FK `ON DELETE CASCADE` to `repos` (repo deletion is a bare `DELETE FROM repos` relying entirely on cascade — `repo-admin.ts`). Also adds `repos.last_repack_at`, the drain watermark, mirroring `last_gc_at` (0004).
- **`encodeDelta`** (`src/pack/delta.ts`): git's delta format writer — block-hash matcher (16-byte blocks, candidate chains capped at 64 like git's own, first-kept so deterministic), COPY sizes capped at 0xFFFF so the 0x10000 zero-size special encoding is never written, present-bit offset bytes. Total (never refuses; caller judges whether the delta beat the whole form), deterministic, no size-ceiling parameter.
- **`createRepack`** (`src/store/repack.ts`): the offline per-repo pass, structurally `createGc`'s sibling. Walks commits oldest-first in deterministic topo order (Kahn, ties by oid; parent ORDER parsed from commit content because `git_edge` kind-2 rows are an unordered set), diffs each root tree against its FIRST parent's, recursing into changed subdirectories — so every changed tree pairs with its same-path predecessor. **Star topology:** a version whose predecessor's anchor already carries `ANCHOR_EVERY − 1 = 31` deltas becomes the next anchor (stored whole); everything else deltas against its segment's anchor, and a delta is kept only when it beats the whole form (git's rule). A delta's base is therefore ALWAYS a whole encoding — depth ≤ 1 structurally, no depth column exists. Phase 2 sweeps everything still pending (non-trees, first-versions, GC-repaired holes) as whole encodings. Never touches an existing row.
- **GC extension — SUPERSEDED 2026-08-16 by D14.** As built on 2026-08-15 this was `gc.ts sweepEncodings` (delete encodings of reclaimed objects and of reclaimed bases; `GcResult` gained `deletedEncodings`). D14 deleted the sweep and the counter: the 0008 FK cascades now remove dependent encoding rows inside the object DELETEs themselves, and `GcResult` carries only `deletedObjects`/`deletedEdges`.
- **Serve** (`src/store/object-store.ts` `buildPack`): unchanged closure; per batch, a LEFT JOIN pulls encodings beside types. A whole encoding is emitted verbatim; a delta is emitted as `REF_DELTA` **iff its base is also in the served set**; otherwise (and for encoding-less or >200 MB objects) the raw path runs exactly as before. Emitted-count must equal the header count or the serve throws. Never emits `OFS_DELTA`, never emits an external-base (thin) delta — see W3.

## Decided — with provenance, in the user's words where the user decided

- **D0 — Goal.** "idiomatically, correctly, and excellently upgrade pggit to handle this entire class of failure by bringing our implementation to git's standards … the fix should resolve both sides, the postgres side and the clone side. also, don't just look at pggit *IN* isolation, look at pggit *IN* contextlayer." (user)
- **D0′ — The standing frame (user, 2026-08-16, stated twice).** "remember, our goal is to build a real backend for git that's powered by postgres. we want to stay close to what git already does, and adapt what makes sense for the postgres world. we're not trying to re-invent git, just layering it on top of postgres. as you implement and come across design or scope decisions, ask me!" This is the rule that adjudicates every fidelity-vs-Postgres-idiom fork; D16's UTF-8 divergence is its one deliberate exception so far.
- **D1 — Derived, never authoritative.** (user: "derived representation first") `git_object` stays the inventory, membership oracle, and raw-content authority; its insert-only property and the published direct-SQL contract (`schema.ts`, `repo_file ⋈ git_object` returns RAW bytes) are untouched. Missing encoding = normal fallback; corrupt encoding = loud error, never a fallback. Accepted cost, eyes open: the canonical ~73 MB does not shrink — that is the producer-side track's and W5's problem. The rejected alternatives (mutate `git_object` in place; a separate authoritative packed tier with loose-row deletion) and why: both codex verdicts, preserved in scratch; short version — in-place changes what `content` MEANS while still typechecking, the two-tier split gives one object two identities with no cross-table uniqueness.
- **D2 — Star topology, `ANCHOR_EVERY = 32`.** (user: "star topology") Depth and base-distance are SEPARATE knobs — the session's central correction. Same-path chains capped at 4 measured 12.85 MB served on the real repo (each cap+1-th version ships whole, and whole versions of a growing tree are the expensive thing); anchors-every-32 with all in-between versions pointing at the anchor measured 5.59 MB at depth ≤ 1 (scratch §F.1/F.2). K≈√N is the structural optimum; 32 fits the motivating lineage (~1,476 versions). An earlier user decision ("agree, set it to 4" for chain depth) was superseded by this measurement — the +10% figure that justified it had capped git's WINDOW search, not same-path chains: right number, wrong evidence.
- **D3 — Our own encoder, structural bases, never a similarity search.** (user: "i think Option B, with the strong ways of testing it you've identified. and note, we should run this on real repos to really verify.") No git shell-out, no window search — pggit walks the commit DAG with real paths in hand, the ground truth git's window heuristic only reconstructs. Libraries-first was discharged before this: no npm library writes git's delta format without adopting an entire git implementation; generic binary-diff formats (xdelta &c.) are unreadable by git.
- **D4 — Frozen, deterministic policy.** Base selection is contextual, not intrinsic (a later branch can introduce new same-path pairs), so "packed once, never revisited" is an ENFORCED policy: oldest-first walk, anchors finalized before dependents, existing rows never rewritten. Both codex runs independently flagged that monotonicity had to be policy, not assumption.
- **D5 — Offline, on the GC drain, GC first.** (user, twice: repack is "another gc-like task"; wiring "to contextlayer at the end") Per repo the drain runs GC then repack over survivors. `last_repack_at` is repack's own watermark — `last_gc_at`'s meaning is not overloaded.
- **D6 — Every object under 200 MB gets an encoding row.** Serve becomes a byte copy for the whole pack, not just trees. The ≥200 MB exclusion mirrors `BIG_OBJECT_BYTES` (the porsager hex-doubling driver cap); such objects always take the chunked raw path.
- **D7 — The tier's hygiene is guaranteed, now by DDL.** After any GC pass no encoding row references a nonexistent object or base. Originally enforced by a `sweepEncodings` query round inside GC; since D14 it is enforced by Postgres itself — the 0008 FK cascades remove dependent encoding rows inside the very DELETE that reclaims an object, so a torn tier is unrepresentable at any crash point. Repack repairs by re-encoding holes whole (see D15). `RepackResult` has NO `repaired` counter — with D5's ordering a dangling delta is never observable to repack, so the counter (present in the reviewed stub) was dropped as dead code during implementation.
- **D8 — Serve rule.** Delta emitted iff base in served set; external-base deltas forbidden until the v2 parser carries `thin-pack` (W3); header-count equality checked before returning.
- **D9 — Read-side ceiling.** (user: "make sure we don't fuck the read side by having too many layers. that should be capped aggressively because reading from a repo is cheaper than reading from pg") This is WHY depth is structural (≤ 1) rather than a checked number, and the constraint any future topology change must re-satisfy.
- **D10 — `git_edge` is its own track.** (user: "open git_edge separately") See W5.
- **D11 — Patch the driver, surgically (2026-08-16).** (user: "agree, pnpm patch the driver with surgical fixes") postgres@3.4.9 — upstream's latest — never settles an in-flight COPY when anything but a clean CommandComplete ends it, and pggit hits every arm of that for real. `patches/postgres.patch` fixes three seams in `connection.js` (ESM + CJS twins): (1) ErrorResponse destroys the copy `stream` and settles its parked `final` callback instead of stashing the error for a ReadyForQuery that cannot help a long-resolved query (hunt H3 — a cancelled push hung forever); (2) `errored()` — the connection-death funnel — settles `final` too, since a connection dying between a copy's `end()` and its CommandComplete otherwise strands the end-promise with no error anywhere (found when two concurrent GC passes hung 60s+ under load); (3) a deferred `nextWrite` against a socket `close()` already nulled fails its callback with CONNECTION_CLOSED instead of throwing an uncatchable TypeError that kills the host process (hunt C5) — and instead of faking success, which would hang a copy stream the same way (2) does. Proven by `pg-txn--copy-cancel-hangs-push-forever` and `pg-txn--txn-death-kills-host-process`.
- **D12 — GC's live set is a TEMP table (2026-08-16).** (user: "(a) make the live set a TEMP table") Each pass runs on ONE reserved connection; `gc_live` is `CREATE TEMP TABLE`, resolved via `pg_temp` ahead of the search path, invisible to every other session, and dropped with the session — collision-proof and leak-proof by construction. Replaces the shared `gc_live_<id>` UNLOGGED table, whose cross-pass collision could truncate a concurrent pass's live set mid-sweep (hunt C1: data loss).
- **D13 — Grace matches git (2026-08-16).** (user: "(a) match git") `graceSeconds` is pggit's `gc.pruneExpire`: the in-flight defense for objects ingested but not yet referenced. At grace 0 a concurrent push can lose its acked closure exactly as git documents for `--prune=now` against live traffic — out of contract, not a defect (hunt C4). The race suite asserts loss-freedom only in its graced arm; a successful clone must be sound at ANY grace.
- **D14 — Referential integrity does the tier's bookkeeping (2026-08-16).** (user: "agree, let postgres' referential integrity handle work for us. in general, i love when we use postgres idioms to cut the code/maintenance we need to do") 0008 gives `git_pack_encoding` two `ON DELETE CASCADE` FKs onto `git_object` — its own oid and its `base_oid` — plus a partial index on `(repo_id, base_oid) where base_oid is not null` so the base-side cascade lookup never seq-scans. `sweepEncodings` is deleted, `GcResult` loses `deletedEncodings`, and the crash window between the object sweep and the encoding sweep (hunt M4) ceases to exist rather than being handled. (Export-shape note, added by the session audit: retiring `deletedEncodings` was an API call the session made while executing this decision, not something the user separately ruled on; it is covered explicitly by the semver-MAJOR the user chose for the spine release — spine doc R19/REL.)
- **D15 — Repair mode after a lossy GC (2026-08-16).** (user: "agree with (b) when a GC pass deleted any encoding rows for a repo, have the next repack run in a 'repair' mode that ignores the early return (full walk) just for that pass"; trigger shape: "(a) No new state — the data itself is the signal") The cascades can hole the tier (a live delta's row dies with its reclaimed base), and D4 forbids rewriting rows — so a repack pass runs a full walk when the data says holes may exist, ignoring the covered-tree early return for RECURSION only, never re-emitting covered rows. The trigger carries NO new state: `repack()` stamps `repos.last_repack_at` itself on success (refining W1's plan, where the drain stamped it — D5's "repack's own watermark" made literal), and repair mode fires iff any pending object's `created_at` predates that stamp — an old object with no encoding row can only be a hole, whatever tore it.
- **D16 — UTF-8, deliberately (2026-08-16).** (user: "pggit should be utf-8 for most of the system, this is where i don't mind diverging with git. utf8 is the modern standard"; scope: "(a) Reject non-UTF-8 tree paths at push ingest too") pggit's text surfaces are valid UTF-8, enforced loudly at the push boundary — a knowing divergence from git's bytes-are-bytes stance. Refnames: the receive-pack command line decodes with `fatal: true`; an undecodable line is a protocol error (a lossy decode would U+FFFD-rename the ref silently and can collide two distinct refnames on one `git_ref` PK value). Provenance honesty (session audit): the reject-loudly MECHANISM for refnames was the agent's derivation from the user's UTF-8 direction, endorsed implicitly by the scope answer's "too" ("reject non-UTF-8 tree paths at push ingest TOO") — it was not itself one of the options the user picked from (the offered refname option had been `bytea` byte-exactness, which the UTF-8 direction superseded). If refname handling is ever revisited, the alternatives are reject-loudly (current), `bytea` byte-exactness, or normalize — weigh against D0′. Tree paths: entry names are validated at object ingest in `validateObject`'s own tree parse (a dedicated pass — `deriveEdges` parses again; the "already parsed" phrasing in earlier drafts overstated the sharing); a non-UTF-8 path fails the push's unpack loudly, so the `repo_file` projection's `path text` is exact and its silent-collision class (two byte-distinct paths collapsing to one U+FFFD row, second silently dropped by `ON CONFLICT DO NOTHING`) vanishes. Cost, eyes open: pggit refuses a push canonical git would accept (e.g. an imported repo with latin1 filenames) — a loud, explainable error, not data loss. The alternative weighed and NOT taken (recorded here because the test that carried its rationale was rewritten): a byte-exact projection with `path bytea`, rejected on 2026-06-22 and again implicitly here, because it makes the published read surface non-text for every SQL consumer to fix one pathological input class. Known coverage gap, accepted: the randomized fuzz/shape corpora migrated to valid-UTF-8 fragments, so the rejection path is covered by dedicated deterministic tests only, not by the differential fuzz (a rejecting server cannot differential-match an accepting git control).
