## The problem, in one paragraph

pggit stored every git object fully inflated and re-deflated each one on every clone, never emitting deltas — a deliberate original design ("spec §3.4 asymmetric kernel", now retired). On a repository whose history is dominated by an append-only directory (one run-UUID subdir added per commit — the shape of CodeCreators' `komal` workspace repo, pggit's motivating production tenant), tree bytes grow quadratically with history: the same growing tree object is rewritten whole by every commit, and trees are ~20-byte binary SHA-1s that intra-object compression cannot touch (lz4 recovers 3% on them — the original schema bet that lz4-TOAST substitutes for delta compression is empirically false on this workload). Measured consequence: a 2 MB-content repo served as a 53.6 MB pack, ~2.4 s of zlib CPU per clone re-deflating unchanged bytes, and a production cold clone racing a 4,950 ms react-router streamed-loader deadline and intermittently losing (customer-visible render failures).

## What was built (the mechanism)

Git's own architecture has three stages: write objects whole, repack offline into delta-compressed packfiles, serve by copying stored bytes. pggit had stages 1 and 3 and no stage 2 — every downstream cost was a symptom of that missing middle leg. This change builds it, as a **derived tier**:

- **`git_pack_encoding`** (migration `0008_pack_encoding.ts`): at most one row per object — `data` is deflated bytes served verbatim (deflate(raw) when `base_oid IS NULL`, deflate(delta program) otherwise), `data_size` is the inflated length of what `data` holds (pack-header varint semantics — the delta PROGRAM length for a delta row, NOT the object's size; `git_object.size` cannot serve both meanings). Hash-partitioned ×16 like its siblings, `STORAGE EXTERNAL` on `data` (already-compressed bytes get no second compression pass), FK `ON DELETE CASCADE` to `repos` (repo deletion is a bare `DELETE FROM repos` relying entirely on cascade — `repo-admin.ts`). Also adds `repos.last_repack_at`, the drain watermark, mirroring `last_gc_at` (0004).
- **`encodeDelta`** (`src/pack/delta.ts`): git's delta format writer — block-hash matcher (16-byte blocks, candidate chains capped at 64 like git's own, first-kept so deterministic), COPY sizes capped at 0xFFFF so the 0x10000 zero-size special encoding is never written, present-bit offset bytes. Total (never refuses; caller judges whether the delta beat the whole form), deterministic, no size-ceiling parameter.
- **`createRepack`** (`src/store/repack.ts`): the offline per-repo pass, structurally `createGc`'s sibling. Walks commits oldest-first in deterministic topo order (Kahn, ties by oid; parent ORDER parsed from commit content because `git_edge` kind-2 rows are an unordered set), diffs each root tree against its FIRST parent's, recursing into changed subdirectories — so every changed tree pairs with its same-path predecessor. **Star topology:** a version whose predecessor's anchor already carries `ANCHOR_EVERY − 1 = 31` deltas becomes the next anchor (stored whole); everything else deltas against its segment's anchor, and a delta is kept only when it beats the whole form (git's rule). A delta's base is therefore ALWAYS a whole encoding — depth ≤ 1 structurally, no depth column exists. Phase 2 sweeps everything still pending (non-trees, first-versions, GC-repaired holes) as whole encodings. Never touches an existing row.
- **GC extension** (`src/store/gc.ts` `sweepEncodings`): after the object sweep, delete encodings of reclaimed objects AND any delta encoding whose base was reclaimed (a force push can orphan an anchor while a delta against it stays reachable — via tree-content reuse across histories). `GcResult` gained `deletedEncodings`.
- **Serve** (`src/store/object-store.ts` `buildPack`): unchanged closure; per batch, a LEFT JOIN pulls encodings beside types. A whole encoding is emitted verbatim; a delta is emitted as `REF_DELTA` **iff its base is also in the served set**; otherwise (and for encoding-less or >200 MB objects) the raw path runs exactly as before. Emitted-count must equal the header count or the serve throws. Never emits `OFS_DELTA`, never emits an external-base (thin) delta — see W3.

## Decided — with provenance, in the user's words where the user decided

- **D0 — Goal.** "idiomatically, correctly, and excellently upgrade pggit to handle this entire class of failure by bringing our implementation to git's standards … the fix should resolve both sides, the postgres side and the clone side. also, don't just look at pggit *IN* isolation, look at pggit *IN* contextlayer." (user)
- **D1 — Derived, never authoritative.** (user: "derived representation first") `git_object` stays the inventory, membership oracle, and raw-content authority; its insert-only property and the published direct-SQL contract (`schema.ts`, `repo_file ⋈ git_object` returns RAW bytes) are untouched. Missing encoding = normal fallback; corrupt encoding = loud error, never a fallback. Accepted cost, eyes open: the canonical ~73 MB does not shrink — that is the producer-side track's and W5's problem. The rejected alternatives (mutate `git_object` in place; a separate authoritative packed tier with loose-row deletion) and why: both codex verdicts, preserved in scratch; short version — in-place changes what `content` MEANS while still typechecking, the two-tier split gives one object two identities with no cross-table uniqueness.
- **D2 — Star topology, `ANCHOR_EVERY = 32`.** (user: "star topology") Depth and base-distance are SEPARATE knobs — the session's central correction. Same-path chains capped at 4 measured 12.85 MB served on the real repo (each cap+1-th version ships whole, and whole versions of a growing tree are the expensive thing); anchors-every-32 with all in-between versions pointing at the anchor measured 5.59 MB at depth ≤ 1 (scratch §F.1/F.2). K≈√N is the structural optimum; 32 fits the motivating lineage (~1,476 versions). An earlier user decision ("agree, set it to 4" for chain depth) was superseded by this measurement — the +10% figure that justified it had capped git's WINDOW search, not same-path chains: right number, wrong evidence.
- **D3 — Our own encoder, structural bases, never a similarity search.** (user: "i think Option B, with the strong ways of testing it you've identified. and note, we should run this on real repos to really verify.") No git shell-out, no window search — pggit walks the commit DAG with real paths in hand, the ground truth git's window heuristic only reconstructs. Libraries-first was discharged before this: no npm library writes git's delta format without adopting an entire git implementation; generic binary-diff formats (xdelta &c.) are unreadable by git.
- **D4 — Frozen, deterministic policy.** Base selection is contextual, not intrinsic (a later branch can introduce new same-path pairs), so "packed once, never revisited" is an ENFORCED policy: oldest-first walk, anchors finalized before dependents, existing rows never rewritten. Both codex runs independently flagged that monotonicity had to be policy, not assumption.
- **D5 — Offline, on the GC drain, GC first.** (user, twice: repack is "another gc-like task"; wiring "to contextlayer at the end") Per repo the drain runs GC then repack over survivors. `last_repack_at` is repack's own watermark — `last_gc_at`'s meaning is not overloaded.
- **D6 — Every object under 200 MB gets an encoding row.** Serve becomes a byte copy for the whole pack, not just trees. The ≥200 MB exclusion mirrors `BIG_OBJECT_BYTES` (the porsager hex-doubling driver cap); such objects always take the chunked raw path.
- **D7 — GC owns the tier's hygiene.** After any GC pass no encoding row references a nonexistent object or base. Repack repairs by re-encoding holes whole. `RepackResult` has NO `repaired` counter — with D5's ordering a dangling delta is never observable to repack, so the counter (present in the reviewed stub) was dropped as dead code during implementation.
- **D8 — Serve rule.** Delta emitted iff base in served set; external-base deltas forbidden until the v2 parser carries `thin-pack` (W3); header-count equality checked before returning.
- **D9 — Read-side ceiling.** (user: "make sure we don't fuck the read side by having too many layers. that should be capped aggressively because reading from a repo is cheaper than reading from pg") This is WHY depth is structural (≤ 1) rather than a checked number, and the constraint any future topology change must re-satisfy.
- **D10 — `git_edge` is its own track.** (user: "open git_edge separately") See W5.

- **W2 — The first drain on live `ctx_pggit` is not a no-op.** GC will hit the entire force-push-era backlog AND repack will backfill every repo in one pass. Komal-sized repo ≈ 10 s locally, but repack reads content via single-row point reads, so against Azure Postgres RTT dominates (unverified estimate: 14k reads × ~30 ms ≈ 7 min for the workspace repo alone, plus every chat-home snapshot repo). Strong recommendation: run the first drain manually in a provisioning window (`platform-only` erect profile per the GC note) before enabling the schedule.
- **W3 — `thin-pack` / `ofs-delta` propagation.** `parseFetch` (`src/protocol/v2.ts`) silently drops both args; `FetchRequest` doesn't carry them. Until it does, incremental fetches whose delta bases live client-side ship those objects WHOLE — correct, just not delta-optimal. Carrying `thin-pack` into `buildPack` unlocks external-base deltas for fetches; the oracle test already covers git's `--fix-thin` ingestion of thin packs. **→ Now measured and load-bearing — see H7 below.**
- **W4 — Streaming / TTFB (unresolved).** pggit materializes the entire pack as one Buffer before the first byte leaves (`buildPack` → Hono body). If react-router's 4,950 ms deadline is time-to-FIRST-byte, streaming is an independent and possibly larger production lever than everything here. NOBODY HAS VERIFIED which it is. Check before declaring the customer symptom fixed. **→ H7 gives this teeth: the delta win does not reach the warm fetch path at all.**
- **W5 — `git_edge` (the bigger database problem).** 299.81 MB on the same repo — 4× `git_object`, 206 MB of it indexes, 1.1 M kind-3 rows growing N²/2, untouched by deltas. Problem statement with candidate directions: `internal/planned/2026-08-15-pggit-git-edge-quadratic.md`. **→ The 2026-08-16 hunt confirmed the curve (exponent 1.99, 85–146× the packfile).**
- **W7 — `repo_file` projection amplification (finding S2 from the 2026-08-16 hunt — BIG, revisit).** Every push rebuilds the branch's whole snapshot: `rebuildRefSnapshot` does a `delete branch → COPY branch back`, so a ONE-FILE push to a 4,096-file tree writes 8,192 `repo_file` rows (4,096 deletes + 4,096 inserts), invariant to how few files changed. Measured **1,428× git's on-disk cost and ~3,101× its WAL** for that one-file push; sustained 60 one-file pushes to a 4,000-file tree left 29.4 MB on disk for 1.5 MB of live rows (19.3×), all of it dead tuples that GC's own long-held snapshot pins the cluster vacuum horizon against, so autovacuum never reclaims them (the horizon-pin mechanism is itself a separate hunt finding — see the reports). The projection performs NO updates, so HOT is structurally unreachable — the entire defence is the dead-tuple threshold plus autovacuum, and GC's own long transactions defeat autovacuum. **Believed fixable without touching the published `repo_file ⋈ git_object` read contract: diff the old and new file lists and write only the delta instead of delete-and-rebuild.** Not designed yet. Evidence: `pg-bloat--push-amplification.ts`, `pg-bloat--repo-file-projection.ts`. We will come back to this.
- **W8 — H7: the delta win does not reach the customer's actual path (revisit with W3+W4).** The cold clone is fixed 9.4×. The PRODUCTION path is not the cold clone — Slate renders via a HEAD-keyed pull-per-navigation, i.e. a warm **incremental fetch** — and the hunt measured that path at **3× to 11× git's transfer, growing with tree size**, with **100% of the server-side cost being closure, 0% pack-encode**. Two independent mechanisms: (a) every new tree's star anchor is an older version of the same path, which the client already has, so D8 forbids the delta and it ships whole (this is exactly what W3 unlocks); (b) a one-commit fetch pays the whole closure walk that a cold clone amortizes over a big pack (this is W4's territory). **So this fix's headline number may not be the number the customer experiences.** This does not undo the work — the repacked remote is still strictly better than the pre-change undeltified serve on the same fetch (measured 0.46×) — but it means "symptom fixed" cannot be claimed until W3/W4 are addressed AND Q3 (is the symptom even still occurring?) is answered against Sentry. Evidence: `wire--pack-shape-vs-git.ts` (11.3×), `perf--incremental-fetch.ts` (40–265×, 100% closure), `realrepo--incremental-fetch-size.ts` (3.07× on contextlayer). We will come back to this.

## The subjective layer — what would otherwise die with this session

**Thoughts.** Derived-first was the right call and the review process (not me) produced it — my original Option A (mutate `git_object`) would have broken the published SQL contract silently. The star invariant earning structural immunity to delta cycles (see Reflections) is the kind of dividend that says the model is right. For W1 I'd extend `drainRepo` rather than add a second scheduler loop — one pass, GC-then-repack, matches D5 and keeps "never overlap per repo" free. I'd gate the first release behind running `perf/delta-corpus.ts` on trove and web checkouts too (30 s each, zero risk — everything mirror-clones).

**Concerns.** C1: `createRepack`'s `contentCache` is unbounded — the pass holds roughly the repo's tree bytes in memory (~80 MB for komal). Fine for the offline drain today; a 10× repo means ~800 MB in the platform process. A bounded cache or per-lineage eviction is the fix if that ever bites. C2: `sweepEncodings` adds a query round to every GC pass; the SCH-10 scheduler test's timing margin narrowed and it flaked once under full-suite contention. If that flake becomes frequent, widen the test's cadence numbers rather than doubting the sweep. C3: repack's per-object point reads (`content()`) are RTT-bound against remote Postgres — see W2; batching reads per diff-level is the optimization if needed, deliberately not built (YAGNI until a real number says so). C4: I asserted inline `STORAGE EXTERNAL` on the partitioned parent propagates to leaf partitions from the 0001 precedent that inline COMPRESSION does — the migration applies and tests pass, but I never ran the one-line catalog check (`select attstorage from pg_attribute` on a leaf). UNVERIFIED EXPECTATION; check before release. C5: `data_size` is `int4` — safe under the 200 MB cap, but if `MAX_ENCODABLE_BYTES` is ever raised past 2 GB it overflows; the two constants are not linked in code.

**Fears.** The one I half-expect: W1 ships, the drain starts in production, and the first pass runs GC-backlog + full-fleet repack backfill concurrently on the customer's Azure instance during business hours — IOPS saturation with no operator watching. Nothing currently guards against this; W2's provisioning-window recommendation is the guard, and it lives only in prose. Second fear: someone quotes "1.56 MB, beats git" (corpus, uncapped chains) as the production serving number (5.72 MB, star) and the 3.7× gap surfaces later as "a regression".

**Questions (load-bearing).** Q1 = W4's TTFB question — gates whether this work alone closes the customer symptom. Q2: how many repos does live `ctx_pggit` hold (workspace + chat-home snapshots)? Fixture-scale trap: the serve test at 80 runs "failed" against a correct implementation because a star's win needs lineages ≫ K — the fixture, not the code, was wrong, and the diagnostic that proved it took ten minutes (`tmp/diag-serve.ts`, gone with the job).

**Curiosities (noticed, not pulled).** The closure already reads every tree body for blob enumeration (`reachability.ts:65`) while kind-3 edge rows drive the recursion — the same structure stored twice; recursing via tree bodies could delete 206 MB of edge index (parked in W5's doc). A `manage.ts repack <repo>` operator verb for targeted backfills. Adaptive K ≈ √(lineage length) instead of the fixed 32 — only with a new sweep on real data.
